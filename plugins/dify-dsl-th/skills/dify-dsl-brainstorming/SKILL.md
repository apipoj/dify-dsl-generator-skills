# dify-dsl-brainstorming

เปลี่ยนโจทย์ที่ยังคลุมเครือให้เป็นแบบที่ทำต่อได้ การคุยให้ชัดยังไม่ใช่การเริ่มสร้างหรือแก้ YAML

เมื่อผู้ใช้ตั้งใจเรียก skill นี้ ห้ามสร้างหรือแก้ DSL หรือส่งต่องานไปขั้นลงมือ ขณะที่ยังมีประเด็นที่ขัดขวางการตัดสินใจ

## ขั้นตอน

1. อ่านบริบทโปรเจกต์ ไฟล์หลัก ข้อจำกัด โครงสร้างโฟลเดอร์ และการเปลี่ยนแปลงล่าสุดที่เกี่ยวข้อง
2. ระบุสิ่งที่ทราบ สิ่งที่ยังไม่ทราบ และเป้าหมายว่าเป็นการสร้างใหม่ ตรวจแบบอ่านอย่างเดียว หรือแก้ไขและปรับปรุง
3. ถามครั้งละหนึ่งประเด็น ใช้คำถามแบบมีตัวเลือกเมื่อช่วยให้ตอบง่าย
4. ถ้าโจทย์ใหญ่เกินไป แบ่งเป็นงานย่อยของ Dify DSL แล้วออกแบบส่วนที่ทำได้จริงก่อน
5. เมื่อข้อมูลชัด ให้เสนอ 2–3 แนวทาง เริ่มจากแนวทางที่แนะนำและอธิบายข้อแลกเปลี่ยน
6. แสดงแบบเป็นส่วนตามความซับซ้อน ให้ผู้ใช้ยืนยันเป้าหมาย ขอบเขต โหมด รูปแบบโหนด การจัดการข้อผิดพลาด และเกณฑ์ยอมรับ
7. จัดรายการสิ่งที่ยังไม่ทราบ แยกเป็น `ขัดขวางงาน` กับ `เลื่อนไว้ก่อนได้`
8. จบ brainstorming ได้เมื่อไม่มีประเด็นขัดขวาง หรือผู้ใช้ยอมรับชัดเจนให้เลื่อนประเด็นที่เหลือ
9. แยกการแสดงร่างข้อความออกจากการเขียนไฟล์ หากผู้ใช้ยอมรับร่างข้อความแล้ว อย่าถือว่าการยังไม่อนุญาตให้เขียนไฟล์เป็นเหตุให้หยุด authoring
10. แนะนำและเลือก skill ถัดไปพร้อมเหตุผล โดยให้ผู้ใช้เปลี่ยนเส้นทางได้

## หลักการถามและเปรียบเทียบ

ถามเป้าหมาย ข้อจำกัด และเกณฑ์สำเร็จก่อนรายละเอียดการทำงาน ตัดสินใจทีละเรื่อง ใช้ข้อมูลการอนุญาตที่ผู้ใช้ให้แล้ว สำหรับ DSL เดิม ต้องแยกการตรวจออกจากการแก้ สำหรับ DSL ใหม่ ต้องแยกร่างข้อความออกจากไฟล์จริง เคารพรูปแบบเดิมของโปรเจกต์ และอย่าเพิ่มงานปรับโครงสร้างหากไม่จำเป็น

ถ้าความต้องการขัดกัน ให้ชี้จุดขัดแย้งก่อน เสนออย่างน้อย 2 แนวทางที่ทำได้จริง หรือ 3 แนวทางสำหรับงานซับซ้อน แต่ละแนวทางต้องมีขอบเขต ประโยชน์ ความเสี่ยง และภาระการตรวจสอบ เลือกวิธีที่เพียงพอต่อเป้าหมาย ไม่ใช่วิธีที่ทำมากที่สุด

## ประเด็นที่ต้องชัดก่อนลงมือ

- สร้างใหม่ ตรวจอ่านอย่างเดียว หรือแก้ไขและปรับโครงสร้าง
- โหมด `workflow`, `advanced-chat` หรือ `rag_pipeline`
- สำหรับการแก้ไข อนุญาตให้เปลี่ยนไฟล์จริงหรือเพียงวิเคราะห์
- สำหรับการสร้าง ต้องการร่างข้อความหรือไฟล์
- เกณฑ์สำเร็จ เช่น นำเข้า staging ได้ เสนอการแก้ขั้นต่ำ หรือเลือกเฉพาะเทมเพลต
- ต้องใช้เทมเพลตหรือเขียนโครงร่างใหม่ได้

หากยังไม่ชัด ให้ถามต่อ เว้นแต่ผู้ใช้ยอมรับให้เลื่อนประเด็นนั้น สำหรับงานใหม่ เมื่อโหมด เป้าหมาย เกณฑ์สำเร็จ และแนวทางเทมเพลตชัด พร้อมยอมรับร่างข้อความแล้ว ให้ไป authoring ได้โดยไม่ต้องรอสิทธิ์เขียนไฟล์

## ผลลัพธ์การออกแบบ

ครอบคลุมบริบทและเป้าหมาย สิ่งที่อยู่นอกขอบเขต ทางเลือกและข้อแลกเปลี่ยน โครงสร้างที่แนะนำและความรับผิดชอบ การไหลของข้อมูล การจัดการข้อผิดพลาดและทางถอย การทดสอบและเกณฑ์ยอมรับ และคำถามคงค้าง หากต้องเขียนเอกสาร ใช้ [แม่แบบการออกแบบ](references/design-doc-template.md)

## ขั้นตอนถัดไป

- สร้าง DSL ใหม่หรือสร้างจากเทมเพลต → [dify-dsl-authoring](../dify-dsl-authoring/SKILL.md)
- ตรวจแบบอ่านอย่างเดียว จัดระดับความเสี่ยง หรือประเมินการนำเข้า → [dify-dsl-review](../dify-dsl-review/SKILL.md)
- แก้ไข ปรับประสิทธิภาพ หรือปรับโครงสร้าง → [dify-dsl-refactor](../dify-dsl-refactor/SKILL.md)
- เป้าหมายยังขัดแย้งหรือมีประเด็นขัดขวาง → อยู่ที่ skill นี้ต่อ

## ภาพประกอบและการตรวจทาน

ใช้ภาพเมื่อช่วยให้เข้าใจชัดกว่าข้อความ มีเครื่องมือจริง และผู้ใช้ยินยอม หากไม่ครบ ให้ใช้ข้อความ ตรวจว่าแบบอธิบายเหตุผล ขอบเขตแต่ละส่วน ขั้นตอนถัดไป เส้นทางข้อผิดพลาด ทางถอย และเกณฑ์ยอมรับครบ โดยไม่เพิ่มงานที่ผู้ใช้ไม่ได้ขอหรือเริ่มทำก่อนเคลียร์ประเด็นขัดขวาง
